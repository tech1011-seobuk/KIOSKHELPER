# 포토이즘 헬퍼

포토이즘·스내피즘 키오스크 고장을 단계별로 진단하고 조치하는 웹앱입니다.
기존 단일 HTML 구조와 GitHub Pages 배포 방식을 유지합니다. 빌드나 패키지 설치는 필요 없습니다.

## 파일 구성

- `index.html`: 화면, 스타일, 계정 기능, 진단 트리, 통계.
- `sw.js`: PWA 캐시 및 오프라인 페이지.
- `manifest.json`, `icon-192.png`, `icon-512.png`: PWA 설정 및 아이콘.
- `DIAGNOSIS_DIAGRAMS.md`: 기존 진단 다이어그램 참고 자료.
- `regression.test.mjs`: 실제 앱 코드에서 함수를 읽어 수행하는 회귀 테스트. 외부 DB에 접속하지 않습니다.
- `preview.mjs`: 로컬 미리보기 서버.

## 수정하고 확인하기

Node.js 22 이상을 사용합니다.

```sh
node --test regression.test.mjs diagnosis.test.mjs
node preview.mjs
```

미리보기 주소는 http://127.0.0.1:4173/ 입니다. 포트 변경은 `node preview.mjs 4174`처럼 지정합니다.
미리보기 앱은 HTML에 설정된 실제 Supabase 프로젝트에 연결됩니다. 운영 계정으로 진단을 클릭하면 실제 이용 기록이 저장됩니다.
자동 회귀 테스트는 가짜 저장소·응답만 사용하므로 운영 기록을 만들지 않습니다.

진단 문구와 연결은 관리자로 로그인한 뒤 **다이어그램 → 증상 선택 → 저장하고 적용**으로 변경합니다. 이미 DB에 저장된 진단은 HTML의 `TREES`를 수정해도 덮어써지지 않습니다. 증상 추가·화면 구조 변경은 코드와 DB를 함께 수정해야 합니다.
미작성 조치 내용은 실제 장비 매뉴얼 또는 담당자 확인 내용을 받은 뒤 채웁니다.

## 배포

운영 저장소: https://github.com/tech1011-seobuk/KIOSKHELPER

운영 사이트: https://tech1011-seobuk.github.io/KIOSKHELPER/

스테이징 저장소: https://github.com/tech1011-seobuk/kioskhelper-staging

스테이징 사이트: https://tech1011-seobuk.github.io/kioskhelper-staging/

1. 최신 원격 변경을 확인하고 필요한 수정을 적용합니다.
2. 회귀 테스트 및 관련 화면을 확인합니다.
3. 앱 파일을 변경했다면 `sw.js`의 `CACHE_NAME` 버전도 올립니다.
4. 스테이징에 먼저 반영하고 배포 성공 및 수정 파일을 확인합니다.
5. 운영에 반영하고 Pages 배포 성공과 실제 URL의 수정 파일을 확인합니다.

GitHub Pages는 기존 `main` 브랜치 기준 배포를 사용합니다. 운영·스테이징의 HTML은 서로 다르므로 운영 파일로 스테이징 전체를 덮어쓰지 않습니다.
특히 스테이징의 다이어그램 편집기와 테스트 표시를 보존합니다.
배포 인증은 GitHub 로그인/인증 도구로 처리하고, 토큰을 소스나 채팅에 기록하지 않습니다.

## 2026-09-11 수정

- 이벤트에 실제 발생 시각을 포함해 오프라인 재전송 후에도 시각을 보존합니다.
- 현재 로그인 사용자의 오프라인 기록만 보내고 다른 계정의 기록은 보관합니다.
- 전송된 기록만 제거하고, 여러 탭에서 동시에 전송하는 작업은 Web Locks로 조정합니다.
- 로그인 후에도 남아 있는 오프라인 기록을 재전송합니다.
- 관리자 조회를 ID 기준으로 나누어 전체 데이터를 읽으며, 조회 오류를 부분 통계로 숨기지 않습니다.
- 관리자 화면을 벗어나거나 로그아웃한 후 도착한 통계 응답은 화면에 표시하지 않습니다.
- 해결 시간 추정 시 브랜드도 함께 구분합니다.
- PWA는 공개 앱 파일과 SDK만 캐시하고, Supabase 응답을 캐시하지 않습니다.
- PWA 업데이트는 해당 환경의 이전 캐시만 정리합니다.

기존 DB 컬럼만 사용하므로 이번 수정에는 SQL 실행이 필요 없습니다.

## 남아 있는 제약

- 운영과 스테이징은 현재 같은 Supabase 프로젝트를 사용합니다. 완전한 데이터 분리는 별도 프로젝트와 인증 URL 설정이 필요합니다.
- 이전 버전이 저장한 오프라인 기록에는 발생 시각이 없어 소급 복원할 수 없습니다.
- 응답을 받기 전에 연결이 끊긴 요청은 서버 반영 여부를 확정할 수 없습니다. 정확히 한 번 기록을 보장하려면 이벤트 고유 ID와 DB 중복 방지 제약을 추가해야 합니다.
- Web Locks 미지원 브라우저는 한 탭 안의 동시 실행만 조정합니다.
- 기기 시계가 잘못 설정되면 새 이벤트의 발생 시각에도 영향이 있습니다.
- 해결 시간은 사용자·브랜드·증상으로 추정합니다. 정확한 진단 회차 연결은 별도 세션 ID 도입이 필요합니다.
- 미완성 진단·색감·교체 안내와 스테이징 편집기의 수동 반영 방식은 기존 상태입니다.
- 제공된 SQL은 새 프로젝트 초기화용입니다. 이번 수정 때문에 기존 운영 DB에 재실행하지 않습니다.

## 진단 저장과 환경 분리

운영 Supabase는 `lsetixbyarexggxsihen`, 테스트 Supabase는 `mjzhljlhjsbnnxyekmwy`입니다. 테스트 DB 지역은 Sydney입니다. 사용자·이용 기록·진단 안내가 분리되어 있습니다. 테스트 코드를 운영에 옮길 때 환경별 URL, 공개 키, 테스트 배너, 오프라인 큐 이름, 서비스 워커 캐시 이름을 유지하세요.

`diagnosis-storage.sql`과 `diagnosis-seed.sql`은 양쪽 DB에 적용되어 있습니다. 초기값은 기존 저장본을 덮어쓰지 않습니다. 관리자의 저장은 revision 비교 후 적용되며 이력은 `diagnosis_tree_revisions`에 남습니다. 직원은 저장할 수 없습니다.

저장 전 수정본은 해당 기기와 계정에 임시 보관됩니다. 저장 성공 후 로그인 또는 새 진단 시작 시 최신 안내를 읽습니다. 동시 수정 충돌은 덮어쓰지 않고 수정본을 유지합니다. 오프라인에서는 최근 캐시 또는 기본 안내임을 표시합니다. 테스트 안내가 자동으로 운영 안내로 승격되지는 않습니다.
